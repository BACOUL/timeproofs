Start · Action File generation flow

Recommended Action File V1 flow

Use this flow after the AI action has already happened in the business system. TimeProofs receives a fingerprint, not the raw client data.

  1. Create the Action File payload with format: "timeproofs.action.v1".
  2. Include the business action: actor, action type, target system, status, proof level and safe references.
  3. Do not include integrity.payload_hash, integrity.file_hash or integrity.seal in the payload that is hashed.
  4. Canonicalize the payload with deterministic JSON ordering.
  5. Compute payload_hash = sha256(canonical_payload).
  6. POST only the hash, action ID and format to /api/seal.
  7. Embed the returned Seal and payload_hash in the final .action.json.
  8. The company stores the final Action File wherever it wants: Drive, SharePoint, S3, CRM, ticketing system or internal archive.
Anti-circular-hash rule: never hash a final file that contains its own hash or Seal. Verification must rebuild the canonical payload with the Seal fields excluded.

Minimal Action File payload before sealing

{
  "format": "timeproofs.action.v1",
  "action_id": "TP-ACT-2026-000001",
  "created_at": "2026-06-18T12:00:00Z",
  "actor": {
    "type": "ai_agent",
    "name": "Support assistant",
    "provider": "OpenAI"
  },
  "action": {
    "type": "support.ticket_created",
    "status": "target_confirmed",
    "target_system": "Zendesk",
    "target_reference": "ticket_12345"
  },
  "traceability": {
    "input_fingerprint": "sha256:<64-hex>",
    "output_fingerprint": "sha256:<64-hex>"
  },
  "proof_level": "target_confirmed"
}

Canonical payload hash

// Pseudocode
const payloadForHash = stripSealFields(actionFile);
const canonicalPayload = canonicalizeJson(payloadForHash);
const payloadHash = sha256(canonicalPayload);

The same payload must always produce the same hash even when object keys arrive in a different order.

Reference · POST /api/seal

Seal an Action File hash

Use /api/seal to create a TimeProofs Seal for a canonical Action File payload hash. Do not send raw prompts, outputs, files, credentials or sensitive client content.

curl -sS https://api.timeproofs.io/api/seal \
  -H "Content-Type: application/json" \
  -d '{
    "payload_hash": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
    "format": "timeproofs.action.v1",
    "action_id": "TP-ACT-2026-000001"
  }'

Example response

{
  "ok": true,
  "seal_id": "seal_01JZTIMEPROOFS000001",
  "sealed_at": "2026-06-18T12:00:02Z",
  "payload_hash": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "format": "timeproofs.action.v1",
  "action_id": "TP-ACT-2026-000001",
  "signature": "<signature>",
  "public_key_id": "timeproofs-main-2026",
  "verify_url": "https://api.timeproofs.io/api/verify-seal?seal_id=seal_01JZTIMEPROOFS000001"
}
Reference · GET/POST /api/verify-seal

Verify a Seal without raw content

A verifier can recalculate the local payload hash from the Action File, then verify the Seal by seal_id or by payload_hash. Sensitive action content should stay local.

# GET by seal_id
curl -sS "https://api.timeproofs.io/api/verify-seal?seal_id=seal_01JZTIMEPROOFS000001"

# POST by seal_id + payload_hash
curl -sS https://api.timeproofs.io/api/verify-seal \
  -H "Content-Type: application/json" \
  -d '{
    "seal_id": "seal_01JZTIMEPROOFS000001",
    "payload_hash": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
  }'

Possible statuses

valid
The Seal exists, signature checks pass, and the payload hash matches when provided.
not_found
No Seal was found for the requested identifier or hash.
invalid_signature
The Seal record or signature is not valid.
unsupported_format
The format is not supported by this verifier.
key_retired
The Seal uses a retired key. It may still be historically verifiable if the key was valid at sealing time.
Compatibility · Existing /timestamp flow

Backward compatibility: /api/timestamp and /api/verify

The legacy timestamp API remains documented for existing .tproof.json users. It is a lower-level proof bundle and should not be confused with an Action File.

# Legacy timestamp proof from a hash
curl -sS https://api.timeproofs.io/api/timestamp \
  -H "Content-Type: application/json" \
  -d '{
    "hash": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
    "type": "document",
    "meta": { "source": "legacy-client" }
  }' | tee proof.tproof.json

# Legacy verify using the .tproof.json bundle
jq -c '{bundle:.}' proof.tproof.json | \
  curl -sS https://api.timeproofs.io/api/verify \
    -H "Content-Type: application/json" \
    -d @-
Compatibility note: .tproof.json proves a timestamped fingerprint. .action.json is the business-level traceability file for an AI action.
Trust · Public keys endpoint

Public keys

Seals include public_key_id. Verifiers should resolve the matching public key from the TimeProofs public keys file and check the signature according to the documented algorithm.

curl -sS https://timeproofs.io/.well-known/timeproofs-keys.json

The key file should expose key IDs, algorithms, creation dates, statuses such as active or retired, and rotation guidance. Do not rely on private keys or unpublished secrets.

Integration patterns · OpenAI / Make / n8n

Common integration flow

The correct integration point is after the external business action succeeds, not before. TimeProofs should record what was declared, executed and confirmed.

OpenAI tools / function calls

1. AI decides to call a tool such as create_support_ticket.
2. Your backend executes the real ticket creation in Zendesk, HubSpot or another system.
3. The target system returns ticket_id, lead_id, message_id or file_id.
4. Your backend builds a TimeProofs Action File with proof_level = "target_confirmed".
5. Your backend hashes the canonical payload and calls /api/seal.
6. Store the final .action.json in the client-controlled archive.

Make scenario

Trigger → AI step → business action module → HTTP /api/seal → store .action.json in Drive, SharePoint, S3 or CRM note

n8n workflow

Webhook/Cron → AI node → target system node → Function node builds Action File → HTTP Request /api/seal → storage node
Safety · Proof limitations

What the API proves and does not prove

  • TimeProofs can show that a canonical payload hash was sealed at a given time by a TimeProofs issuer key.
  • TimeProofs can help verify that an Action File was not modified after sealing, if the verifier rebuilds the same canonical payload hash.
  • TimeProofs does not prove that the AI was correct.
  • TimeProofs does not guarantee legal validity of the underlying action.
  • TimeProofs does not replace technical logs; it complements them with a portable business artifact.
  • Customers remain responsible for Action File content and for storing original evidence.
