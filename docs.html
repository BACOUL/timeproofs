0. Quickstart — TimeProofs in 30 seconds

The core flow is always the same:

  1. Hash your data locally (SHA-256) — file, text, dataset, model, etc.
  2. Call POST /api/timestamp with the hash.
  3. Store the returned proof or .tproof.json bundle next to the data (same folder, DB record, or object).
  4. Verify later: online with v0.1, offline with v0.2 bundles.

TimeProofs never receives your files or AI outputs — only SHA-256 hashes and small, non-sensitive metadata. 

# cURL — create a proof (v0.1, online verify)
curl -s -X POST https://api.timeproofs.io/api/timestamp \
  -H "Content-Type: application/json" \
  -d '{"hash":"<SHA256_HEX>"}'
// Browser (conceptual) — text → hash → timestamp
async function sha256Hex(str){
  const buf = new TextEncoder().encode(str);
  const digest = await crypto.subtle.digest("SHA-256", buf);
  return [...new Uint8Array(digest)]
    .map(b => b.toString(16).padStart(2,"0"))
    .join("");
}

const API  = "https://api.timeproofs.io/api";
const hash = await sha256Hex("hello");

const proof = await fetch(`${API}/timestamp`, {
  method: "POST",
  headers: { "Content-Type":"application/json" },
  body: JSON.stringify({ hash })
}).then(r => r.json());
// Node (conceptual) — using the v0.2 SDK (Preview)
import { TimeProofsV02 } from "./sdk/timeproofs-v02.js";

const client = TimeProofsV02.createClient({
  baseUrl: "https://timeproofs-api-v02.jeason-bacoul.workers.dev"
});

const hash   = await client.hashText("hello");
const tsResp = await client.timestamp(hash);
const bundle = client.createBundle({
  hash:      tsResp.hash,
  timestamp: tsResp.timestamp,
  proof:     tsResp.proof,
  meta:      { type: "document", purpose: "release" }
});

// Later, offline:
const result = await client.verifyBundle(bundle, { file: null });
if (result.valid) {
  console.log("Bundle is structurally valid and matches the expected hash.");
}

1. 5-minute integration (minimal)

Three short paths — keep it minimal, reproducible, and hash-only.

1.1 Node 18+ — hash → timestamp → write bundle file

// (Conceptual) Node 18+: compute sha256, call timestamp, store bundle JSON next to your file.
// You can use the SDK (recommended) or plain fetch + JSON.

1.2 Browser — file → hash → timestamp → download bundle

// (Conceptual) Browser: user selects a File, you sha256 it locally, call /api/timestamp,
// then let the user download proof.tproof.json (no file upload).

1.3 Offline verify — bundle + file → result

// (Conceptual) Offline: verify bundle structure + (optionally) verify that a given file hashes to bundle.hash.value.
// No network required.
Production notes (short):
  • Hash normalization: define UTF-8 + EOL rules for text; treat binaries as bytes.
  • Large files: prefer streaming hashing (avoid reading multi-GB into memory).
  • Network: add timeout + retry (idempotent calls) and handle 429.
  • Metadata: keep meta small; no secrets/PII.

2. Security model (what it proves / what it doesn’t)

TimeProofs is a proof-of-existence and integrity mechanism for a SHA-256 hash. It proves that a given hash existed at or before the issued timestamp, and that the content has not changed later if it still hashes to the same value.

It does not prove authorship, identity, truthfulness, originality, license, or who had access to the content. If you need authorship, add separate identity/signing workflows (e.g., user signatures, legal processes, or third-party attestations).

3. Overview & versions

TimeProofs exposes a small HTTP API. You always hash locally, send only the hash, and get back a signed proof. There are two compatible versions:

  • v0.1 (production, online verify) — hash-only inputs, events stored server-side, /api/verify available for public lookups.
  • v0.2 (Preview, stateless) — the server never stores proofs; you keep a signed timestamp object and verify offline using .tproof.json bundles.

Use v0.1 for a simple online verification API (/api/verify) with server-side storage. Use v0.2 when you want stateless proofs, portable .tproof.json bundles, and offline verification.

4. Choose your integration

Pick the path that matches how your product is built. The API flow remains the same; only where you hash and store bundles changes.

You have…UseReason
Static site / front-end only v0.1 with browser hashing Hash in the browser, call /api/timestamp, show the proof or link to users.
Backend app / monolith v0.1 from your server Hash in your backend, call /api/timestamp, store hash + proof in your database.
Serverless / edge pipeline v0.2 bundles (Preview) Call the stateless endpoint, keep the timestamp object, build .tproof.json bundles, verify offline.
AI / data / model workflows v0.2 + SDK/CLI (Preview) Attach bundles to datasets, jobs, or model versions and verify later in audits or pipelines.

You can mix both: for example, use v0.1 for public web verification and v0.2 bundles for internal pipelines.

5. What’s new in v0.2 (Preview)

  • Stateless API — timestamp responses are not stored server-side; you keep the proof.
  • .tproof.json bundles — self-describing proof bundles containing hash, algorithm, timestamp, signatures, and metadata.
  • Offline verification — verify bundles entirely offline using the SDK/CLI or your own verifier.
  • Structured metadata — normalized meta.type, meta.domain, and meta.purpose fields to support audit workflows.

Notes on cryptography in v0.2: signature mechanisms and public key distribution (e.g., JWKS) may evolve during preview. This page will only claim specific endpoints once they are published and stable.

8. POST /api/timestamp

Create a timestamped proof for a SHA-256 hash (v0.1 semantics).

POST /api/timestamp
Content-Type: application/json
Authorization: Bearer <TOKEN>

{
  "hash": "7c040f...d76c2",
  "meta": { "type": "file", "hint": "optional-small-note" }
}
# cURL (v0.1)
curl -s -X POST https://api.timeproofs.io/api/timestamp \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"hash":"<SHA256_HEX>","meta":{"type":"file"}}'
// JS (browser, v0.1-style) — string → sha256
async function sha256Hex(str){
  const buf=new TextEncoder().encode(str);
  const digest=await crypto.subtle.digest('SHA-256', buf);
  return [...new Uint8Array(digest)]
    .map(b=>b.toString(16).padStart(2,'0'))
    .join('');
}

const API="https://api.timeproofs.io/api";
const hash=await sha256Hex("hello");

const proof=await fetch(`${API}/timestamp`,{
  method:"POST",
  headers:{
    "Authorization":"Bearer <TOKEN>",
    "Content-Type":"application/json"
  },
  body:JSON.stringify({ hash, meta:{ type:"text" } })
}).then(r=>r.json());
FieldTypeRequiredDescription
hashstringyesLowercase hex SHA-256 of your content
metaobjectnoSmall hints. Avoid secrets/PII

In v0.2 (Preview), POST /api/timestamp returns a structured timestamp object and does not store it server-side. Clients embed it into a local bundle and verify offline.

9. GET/POST /api/verify

Check an existing proof by hash (v0.1 online verification).

GET /api/verify?hash=<SHA256_HEX>
# cURL (v0.1)
curl -s "https://api.timeproofs.io/api/verify?hash=<SHA256_HEX>"
// JS (v0.1)
const API="https://api.timeproofs.io/api";
const res=await fetch(`${API}/verify?hash=${encodeURIComponent(hash)}`);
const data=await res.json();

v0.1 exposes public read-only verification. In v0.2 (Preview), /api/verify may be disabled (e.g. 501): verification is performed offline by validating .tproof.json bundles with the SDK/CLI or any compliant verifier.

14. Client helpers & SDK

// File → sha256 (browser)
async function sha256FileHex(file){
  const buf=await file.arrayBuffer();
  const digest=await crypto.subtle.digest('SHA-256', buf);
  return [...new Uint8Array(digest)]
    .map(b=>b.toString(16).padStart(2,'0'))
    .join('');
}
// Node.js
import { createHash } from "crypto";

const sha256Hex = (buf) =>
  createHash("sha256").update(buf).digest("hex");

v0.2 (Preview) ships a minimal JS SDK (browser + Node 18+) that wraps hashing, timestamp calls, bundle creation and offline verification: 

// JS SDK v0.2 (path inside repo)
/sdk/timeproofs-v02.js

// Example usage (conceptual)
const client = TimeProofsV02.createClient({
  baseUrl: "https://timeproofs-api-v02.jeason-bacoul.workers.dev"
});

const hash   = await client.hashText("hello");
const tsResp = await client.timestamp(hash);
const bundle = client.createBundle({
  hash:      tsResp.hash,
  timestamp: tsResp.timestamp,
  proof:     tsResp.proof,
  meta:      { type:"document", purpose:"release" }
});

const verifyResult = await client.verifyBundle(bundle, { file: null });
// verifyResult.valid tells you if the bundle is structurally sound and, if a file is provided, if the hash matches.
// Offline verify (v0.2) — given a stored .tproof.json bundle
import { TimeProofsV02 } from "./sdk/timeproofs-v02.js";

// In a Node context; in a browser you would use a File/Blob instead.
import fs from "node:fs/promises";

const bundleJson = await fs.readFile("proof.tproof.json", "utf8");
const bundle = JSON.parse(bundleJson);

const result = await TimeProofsV02.verifyBundle(bundle, { file: null });

if (result.valid) {
  console.log("Proof is valid and the bundle structure matches the TimeProofs v0.2 spec.");
} else {
  console.error("Invalid bundle:", result.reason || "unknown reason");
}

The SDK never uploads files. It only works with hashes and locally available metadata and bundles. Offline verification lets you validate proofs even in air-gapped environments.

15. Root files & related protocols

TimeProofs can read and reference a set of independent “root” metadata files exposed by your site or service. These files are not owned by TimeProofs; they are standalone protocols that can be used with or without TimeProofs.

  • /robots.txt — crawling and indexing policy.
  • /.well-known/security.txt — security contact and disclosure rules.
  • /humans.txt — team, credits and ethical commitments.
  • /integrity.txt — independent integrity protocol (tracking, cookies, data-use/logs, third-parties, accessibility).
  • /authenticity.txt — independent authenticity protocol (origin, AI involvement, human review, AI visibility, authenticity updates).
  • /rights.txt — independent rights protocol (rights-model, allowed/forbidden uses, licence, rights-update policy).
  • /explainable-ia.txt — independent explainability protocol (ai-systems, ai-uses, io-handling, explanations, limitations).

TimeProofs may include references to these root files in .tproof.json bundles (for example via meta) but never replaces them. They remain independent standards that any site, API, or AI system can adopt.
