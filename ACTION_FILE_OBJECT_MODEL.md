# TimeProofs V1 Action File Object Model

## Purpose

TimeProofs is the black box for AI actions. This document defines the TimeProofs V1 object model before any implementation work begins.

The goal is to prevent confusion between the customer-owned record of an AI action, the fingerprint that TimeProofs seals, and the portable proof object used for verification. A clear object model is needed before API design, SDK changes, schema work, generator work, or verification UI changes.

This document is intentionally conceptual. It does not create a schema, change API behavior, change SDK behavior, or define canonicalization code.

## Definitions

### AI Action File

An AI Action File is the customer-owned traceability file for one observable AI action. It is the business-readable record that explains what happened, which system or workflow produced the action, when it happened, and what local evidence or references the company wants to keep.

The AI Action File belongs to the customer. The company stores it wherever it wants: in its own systems, document storage, CRM, ticketing system, audit repository, evidence store, or other internal location.

TimeProofs must not receive the AI Action File by default.

### Seal

A Seal is the TimeProofs signed receipt or proof for an AI Action File fingerprint. It records that TimeProofs sealed a specific fingerprint at a specific time using specific sealing metadata.

A Seal proves the fingerprint that was submitted for sealing. It does not require sensitive action content and must not require the full AI Action File by default.

### Proof Bundle

A Proof Bundle is the existing or future portable proof object used to verify a sealed fingerprint. Existing `.tproof.json` proof bundles remain the current backward-compatible proof bundle format.

A Proof Bundle helps a verifier check that a fingerprint was sealed. It should not be confused with the AI Action File itself.

### Fingerprint

A fingerprint is the deterministic digest of the hashable AI Action File core. It is produced locally before sealing. TimeProofs seals the fingerprint, not sensitive action content.

Future specifications must define deterministic canonicalization before a stable `.action.json` format can be implemented.

### Observable AI Action

An observable AI action is a concrete business action or system-visible event caused, assisted, or generated by an AI workflow. Examples include creating a CRM lead, creating a support ticket, sending an email, generating a document, updating a CRM record, or classifying a request.

The action must be observable enough for the company to describe it and keep local evidence or references for it.

### Customer-Owned Evidence

Customer-owned evidence is any record, file, pointer, log reference, internal ID, document, ticket, CRM object, audit note, or trace kept by the company in its own environment.

TimeProofs may help seal the fingerprint of an evidence file, but the company controls the evidence and storage location.

### Sensitive Action Content

Sensitive action content is any data that the company should not send to TimeProofs by default. This can include personal data, customer data, prompts, model outputs, confidential business content, documents, emails, CRM records, internal notes, credentials, regulated data, or proprietary workflow details.

Sensitive action content may exist inside the customer's own AI Action File if the company chooses to store it locally. It must not be uploaded to TimeProofs by default.

## Object Boundaries

### AI Action File Boundary

The AI Action File is the record.

It is customer-owned and stored by the company. It may contain:

- action summary
- system ID
- workflow ID
- action timestamp
- actor or automation identifiers
- model or tool references when appropriate
- business object references
- redaction notes
- internal IDs
- local evidence pointers
- links or references to technical logs
- customer-controlled context

It may contain sensitive content only if the company chooses to store that content locally in its own environment.

It must stay outside TimeProofs by default. TimeProofs should not require the full AI Action File to seal or verify a fingerprint.

### Seal Boundary

The Seal is the TimeProofs receipt for a fingerprint.

It is created by TimeProofs and should include sealing metadata such as:

- issuer
- issuedAt
- nonce
- keyId
- algorithm
- sealed fingerprint
- signature or proof fields
- verification metadata needed to check the seal

The Seal must not require sensitive action content. It should be designed around fingerprint-only sealing by default.

### Proof Bundle Boundary

The Proof Bundle is the portable verification object.

It must remain compatible with existing `.tproof.json` proof bundles. It can prove that a fingerprint was sealed and provide the information needed to verify that proof.

The Proof Bundle should not be treated as the AI Action File. It is proof metadata for a fingerprint, not the customer-owned action record itself.

## Relationship Between The Objects

The conceptual relationship is:

AI Action File -> local canonical fingerprint -> Seal / Proof Bundle -> verification

The AI Action File is the record. The fingerprint is the digest of that record. The Seal proves that TimeProofs sealed that fingerprint. The Proof Bundle helps verify the seal. The company keeps the AI Action File.

This separation is central to the TimeProofs privacy model:

- the company creates the AI Action File locally
- the company computes the fingerprint locally
- TimeProofs receives the fingerprint and minimal sealing metadata by default
- TimeProofs returns a Seal or Proof Bundle for verification
- the company stores the AI Action File and any sensitive context it chooses to keep

## Future `.action.json` Direction

`.action.json` is future work. This PR does not create a `.action.json` schema, example, generator, API, SDK helper, or verification behavior.

The intended role of `.action.json` is to represent the AI Action File: the customer-owned traceability file for one observable AI action.

`.tproof.json` remains the existing proof bundle format. Existing `.tproof.json` verification must remain backward-compatible.

`.action.json` and `.tproof.json` must not be merged into one confusing object:

- `.action.json` should represent the AI Action File record
- `.tproof.json` should remain a proof bundle or sealing primitive
- a Seal or Proof Bundle can reference the fingerprint of an AI Action File
- verification can compare the local `.action.json` fingerprint against the sealed fingerprint

Future design work should keep the objects separate unless a later specification defines a safe and clearly named envelope.

## Fingerprinting And Canonicalization Principles

These are high-level principles only. This document does not implement canonicalization.

Future canonicalization must be deterministic. The same hashable AI Action File core must always produce the same fingerprint.

The fingerprint must not include fields that change after sealing. Mutable fields can create false mismatches and should remain outside the hashable core unless a later specification defines a stable rule.

The model must avoid circular hashing. The Seal, signature, proof fields, or sealed fingerprint must not be included inside the data that is hashed to produce that same fingerprint.

A detached Seal is preferred. Seal and proof data should remain outside the hashable AI Action File core unless a later specification defines otherwise.

The object model should support clear separation between:

- hashable action-file core
- non-hashable local annotations
- detached Seal
- detached or linked Proof Bundle
- verification result generated later by a verifier

## Sensitive-Content Boundary

TimeProofs must not receive sensitive action content by default.

Customers may store sensitive context in their own AI Action File if they choose. That storage decision belongs to the customer and should happen inside the customer's environment.

TimeProofs should receive only:

- the fingerprint
- minimal sealing metadata needed to issue and verify the Seal
- no prompts, outputs, customer records, emails, documents, or business content by default

Examples in future documentation, tests, or demos must use synthetic or redacted data.

The default privacy model is hash-only and fingerprint-only. Any feature that sends more than a fingerprint must be explicit, justified, documented, and outside the default path.

## Verification Model

Future AI Action File verification should work conceptually as follows:

1. Load the AI Action File locally.
2. Canonicalize the hashable action-file core locally.
3. Compute the fingerprint locally.
4. Load or read the Seal or Proof Bundle.
5. Verify the Seal or Proof Bundle.
6. Compare the local fingerprint to the sealed fingerprint.
7. Display whether the local AI Action File still matches the sealed fingerprint.

Verification should make the object boundaries visible:

- the AI Action File is the customer-owned record
- the fingerprint is computed locally from that record
- the Seal proves TimeProofs sealed that fingerprint
- the Proof Bundle helps verify the Seal
- the verification result is an interpretation of the local check, not a legal or compliance guarantee

## Backward Compatibility

Existing `.tproof.json` proof bundles remain valid.

Existing `/api/timestamp` and `/api/verify` behavior must not be broken by future Action File work.

Existing SDK helpers should remain compatible. New Action File support should be additive rather than replacing existing proof-bundle helpers.

Future `.action.json` support must not break existing `.tproof.json` verification.

A safe migration path should preserve the existing proof-of-existence primitives while adding AI Action File support on top of them.

## Non-Goals

This PR does not include:

- API changes
- SDK changes
- schema creation
- `.action.json` examples
- canonicalization code
- generator implementation
- verification behavior changes
- website implementation changes
- dashboard creation
- changes to `selfhost/server.js`
- OpenAPI behavior changes
- legal advice
- compliance certification
- a guarantee of legal validity
- replacement of technical logs

TimeProofs complements technical logs. It does not replace them.

TimeProofs supports traceability evidence for fingerprints. It does not prove that the AI was correct, that the content is true, or that a legal or regulatory requirement has been fully satisfied.
