Protocol — ProofSpec

Open, normative specification to prove when data existed and that it has not changed. Hash-only inputs, signed timestamps, public verification.

Overview

ProofSpec defines how to create, sign, publish, and verify digital proofs of existence.

Model: hash locally → get a signed, timestamped proof → anyone can verify later without access to your original data.

This document is normative for issuers and verifiers that claim to be ProofSpec v0.1 compliant.

ProofSpec v0.1 vs TimeProofs v0.2

  • ProofSpec defines the proof object, signing rules, verification behaviour, and error semantics.
  • TimeProofs v0.2 is a stateless reference implementation: hash-only API, public verification, and portable .tproof.json bundles that can be inspected offline.

File date ≠ proof

  • A file date is local, easy to change, and not independently verifiable.
  • A ProofSpec proof is a signed timestamp bound to an exact hash, verifiable by third parties later.

What it proves / What it does NOT prove

It proves:

  • That specific bytes (identified by hash) existed at or before ts.
  • That the proof was issued by the declared issuer key (alg/kid).

It does NOT prove:

  • Authorship, ownership, intent, or legal status.
  • Truthfulness/accuracy of the content, only integrity and timing.
  • Any claim about the original content if the hash was computed over different bytes.

Normative language & scope

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY in this document are to be interpreted as described in RFC 2119 and RFC 8174.

  • This specification applies to the structure of proof objects, signing rules, verification behaviour, and error reporting.
  • Implementation details (storage engine, infrastructure, billing, UI) are non-normative unless explicitly stated.
  • Where this document uses “example”, the content is informative and does not create additional normative requirements.

Conformance

The following roles are defined:

  • Issuer: a system that accepts a hash and returns a signed proof object.
  • Verifier: a system that checks a proof object and returns a validation result.
  • Client: any caller (app, backend, CLI, agent) that interacts with an issuer or verifier.

A ProofSpec-compliant Issuer:

  • MUST only accept canonical hashes (see Canonicalization) and MUST NOT require original content.
  • MUST produce proof objects that satisfy the JSON schema and data model.
  • MUST sign over a deterministic message that includes at least hash and ts.
  • SHOULD expose a stable verify URL for each hash.

A ProofSpec-compliant Verifier:

  • MUST validate the structure of the proof object, including required fields and formats.
  • MUST recompute the expected signature for the given alg and compare using a timing-safe method.
  • MUST reject proofs whose ts is not a valid UTC timestamp or is unreasonably far in the future.
  • SHOULD provide clear error codes as defined in the Errors section.

Clients that claim ProofSpec compliance SHOULD keep the full proof JSON and SHOULD NOT rely only on a verify URL.

Canonicalization

  • Issuers and clients MUST hash the exact bytes they intend to prove (“bytes-in, bytes-out”).
  • Text inputs SHOULD be encoded as UTF-8 and SHOULD normalize line endings to LF (\n) before hashing.
  • If a client applies any preprocessing (whitespace normalization, JSON stable stringification, etc.), it MUST be documented and MUST be applied consistently for verification.

Note: This section defines the ProofSpec v0.1 proof object. TimeProofs v0.2 ships a .tproof.json bundle wrapper for portability (see TimeProofs v0.2 bundle).

Proof object (ProofSpec v0.1)

{
  "hash":"<64-hex>",
  "ts":"2025-01-01T00:00:00.000Z",
  "sig":"<64-hex>",
  "alg":"HMAC-SHA256",
  "kid":"v1",
  "issuer":"example-issuer",
  "verify_url":"https://example-issuer.example/verify?hash=...",
  "meta":{
    "type":"event",
    "source":"web"
  }
}

The canonical signature encoding in ProofSpec v0.1 is lowercase hex (64 chars). Implementations MUST document any deviation.

Signing

Issuers MUST sign a deterministic message. The reference message format used here is:

<hash>|<ts>
// Node.js HMAC verify (example)
import crypto from "node:crypto";

function verifyHmac({ hash, ts, sig }, secret) {
  const msg = `${hash}|${ts}`;
  const expect = crypto
    .createHmac("sha256", secret)
    .update(msg)
    .digest("hex");

  return crypto.timingSafeEqual(
    Buffer.from(expect, "hex"),
    Buffer.from(sig, "hex")
  );
}

Issuers SHOULD implement key rotation and include kid to identify the signing key version.

Validation

  • hash MUST be a 64-character lowercase hex string.
  • ts MUST be a valid ISO 8601 UTC timestamp and SHOULD NOT be in the future beyond a reasonable tolerance.
  • sig MUST be lowercase hex (64 chars) when alg is HMAC-SHA256.
  • The verifier MUST recompute the expected signature according to alg/kid and compare using a timing-safe method.
  • If any required field is missing or invalid, the verifier MUST return a failure with an appropriate error code.

JSON schema

{
  "$schema":"https://json-schema.org/draft/2020-12/schema",
  "type":"object",
  "required":["hash","ts","sig","alg"],
  "properties":{
    "hash":{"type":"string","pattern":"^[a-f0-9]{64}$"},
    "ts":{"type":"string","format":"date-time"},

Verification

GET /api/verify?hash=<64-hex>
→ {"ok":true,"valid":true,"timestamp":"2025-01-01T00:00:00.000Z","hash":"..."}

Response fields are issuer-defined as long as the verification result is unambiguous.

Verify URL

The verify URL is a stable endpoint that returns JSON status for the given hash (or proof). It SHOULD be included in the proof JSON as verify_url.

Clients MAY choose to rely on the verify URL alone, but keeping the full proof JSON is RECOMMENDED for long-term verification.

TimeProofs v0.2 bundle (.tproof.json)

TimeProofs v0.2 uses a portable wrapper bundle designed for offline inspection and long-term storage. The bundle MUST NOT contain original content, secrets, or personal data.

{
  "version":"timeproofs-0.2",
  "proof":{
    "hash":"<64-hex>",
    "ts":"2025-01-01T00:00:00.000Z",
    "sig":"<64-hex>",
    "alg":"HMAC-SHA256",
    "kid":"v1",
    "issuer":"timeproofs.io",
    "verify_url":"https://api.timeproofs.io/api/verify?hash=..."
  },
  "meta":{
    "type":"document",
    "purpose":"release",
    "tool":"timeproofs-web"
  }
}
  • Offline inspection: The bundle is readable without contacting the issuer.
  • Online verification: A verifier MAY call verify_url to re-check status later.
  • Metadata: meta is optional, local-only, and MUST NOT contain personal data or secrets.

Mapping (ProofSpec → TimeProofs bundle)

The bundle wraps a ProofSpec v0.1 proof object under proof. Mapping is 1:1:

Reserved fields

Names starting with _tp_ are reserved for the ProofSpec and MUST NOT be used for custom metadata.

Operational policy

  • Issuers SHOULD keep minimal logs and avoid storing original content.
  • Issuers SHOULD apply rate limits and abuse protection on timestamp and verify endpoints.
  • Key rotation SHOULD be implemented using kid and a clear key lifecycle policy.

Checklist

  • Hash locally (no original content leaves the device).
  • Hash the exact bytes you intend to prove (apply the same canonicalization every time).
  • Keep the proof JSON (.tproof.json) for long-term verification.
  • Validate required fields and formats; verify signatures using timing-safe comparison.
  • Prefer a stable verify_url for public re-checks.

Versioning

This document describes ProofSpec v0.1. Additive changes SHOULD prefer minor/patch bumps; breaking changes MUST bump the major version.

Issuers and verifiers SHOULD clearly expose which ProofSpec version(s) they support.
