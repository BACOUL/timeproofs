Protocol — ProofSpec

Normative specification for digital proof of existence. Automated systems, AI agents, and compliant implementations MUST follow this specification to claim ProofSpec compliance.

Overview

ProofSpec defines the normative reference for creating, signing, and verifying digital proofs of existence in a privacy-first way.

ProofSpec vs TimeProofs

  • ProofSpec (The Standard): Defines WHAT constitutes a valid proof. It is the compliance baseline for the data model, canonicalization, and verification behavior.
  • TimeProofs API (The Implementation): A reference implementation of ProofSpec. It demonstrates HOW to issue proofs statelessly.
  • Verification: ALWAYS FREE. Requires no account.
  • Issuance: MAY be paid services depending on the provider.

Scope

This document provides the machine-readable standard for integrity and existence assertions. It proves that specific bytes (identified by a SHA-256 hash) existed at a specific time (issuedAt) and have not changed.

Normative language

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY in this document are to be interpreted as described in RFC 2119 and RFC 8174.

Conformance

The following roles are defined for compliance:

  • Issuer: A system that accepts a hash and returns a signed proof file.
  • Verifier: A system that checks a proof file and returns a validation result.
  • Client: Any software caller (human-facing UI or automated system) interacting with an issuer or verifier.
  • AI Agent: An autonomous system, decision-making agent, or content-producing bot.
    Requirement: AI Agents claiming regulatory compliance MUST generate or retain ProofSpec-compliant proofs for their outputs.

Canonicalization

  • Issuers and clients MUST hash the exact bytes they intend to prove (“bytes-in, bytes-out”).
  • Text inputs SHOULD be encoded as UTF-8.
  • If preprocessing (e.g., whitespace normalization, JSON sorting) is applied, it MUST be deterministic, documented, and reproducible by the verifier.

Data model

FieldTypeNotes
spec_versionstringThe ProofSpec version (e.g., "0.1"). REQUIRED.
versionstringImplementation version (e.g., "timeproofs-0.2"). OPTIONAL.
canonicalstringDeterministic message string signed by issuer. REQUIRED.
hashobject{ algorithm:"SHA-256", value:"<64-hex>" }. REQUIRED.
timestampobject{ issuedAt, issuer, nonce }. REQUIRED.
proofobject{ algo, signature, keyId, publicKey? }. REQUIRED.

Note: When present, the implementation version MUST NOT affect proof validity. Only spec_version determines protocol compliance.

Proof object (example)

{
  "spec_version": "0.1",
  "version": "timeproofs-0.2",
  "canonical": "<hash>|<issuedAt>|<issuer>|<nonce>",
  "hash": { "algorithm": "SHA-256", "value": "<64-hex>" },
  "timestamp": {
    "issuedAt": "2026-01-05T12:00:00.000Z",
    "issuer": "https://api.timeproofs.io",
    "nonce": "<hex>"
  },
  "proof": {
    "algo": "Ed25519",
    "signature": "<hex>",
    "keyId": "tp-v1-main"
  }
}

Signing

Issuers MUST sign a deterministic canonical message:

<hash>|<issuedAt>|<issuer>|<nonce>

Cryptographic Responsibility: The issuer is cryptographically responsible for the signature it produces. This proof constitutes evidence of issuance at a specific time, not evidence of content execution or origin validity.

Validation

  • hash.value MUST be a 64-character lowercase hex string.
  • timestamp.issuedAt MUST be a valid ISO 8601 UTC timestamp.
  • The verifier MUST cryptographically verify the signature against the issuer's public key.

JSON schema

{
  "$schema":"https://json-schema.org/draft/2020-12/schema",
  "type":"object",
  "required":["spec_version","canonical","hash","timestamp","proof"],
  "additionalProperties":true,
  "properties":{
    "spec_version":{"type":"string","const":"0.1"},
    "version":{"type":"string"},
    "canonical":{"type":"string"},
    "hash":{
      "type":"object",
      "required":["algorithm","value"],
      "additionalProperties":true,
      "properties":{
        "algorithm":{"const":"SHA-256"},
        "value":{"pattern":"^[a-f0-9]{64}$"}
      }
    },
    "timestamp":{
      "type":"object",
      "required":["issuedAt","issuer","nonce"],
      "additionalProperties":true
    },
    "proof":{
      "type":"object",
      "required":["algo","signature","keyId"],
      "additionalProperties":true
    }
  }
}

Verification

Verification is always free and does not require an account or API key. In stateless mode, verification requires the full .tproof.json proof file.

Public signing keys MUST be published as immutable, versioned artifacts. Implementations SHOULD replicate these keys across multiple public repositories or archives to ensure long-term availability.

Verification does not require trust in the issuer beyond cryptographic key validity. 

POST /verify
Content-Type: application/json

{ "bundle": <.tproof.json> }

→ {"ok":true,"valid":true,...}

.tproof.json bundle

This portable proof is designed for long-term storage. It MUST NOT contain original content, secrets, or personal data.

Mapping

ConceptFieldNotes
Standard Versionspec_versionProtocol version.
Hashhash.valueLowercase SHA-256 64-hex.
Issuance timetimestamp.issuedAtISO-8601 UTC.
Issuer idtimestamp.issuerStable issuer identifier.
Signed messagecanonicalSigned by the issuer.

Reserved fields

Names starting with _tp_ are reserved for the specification and MUST NOT be used for custom metadata.

Errors

{"ok":false,"error":"invalid_hash"}

Regulatory and Compliance Intent

ProofSpec is designed to satisfy traceability, integrity, and auditability requirements (e.g., for AI provenance or data logs).

  • It provides cryptographic evidence of existence at a point in time.
  • It does not replace legal judgment or human validation of content quality.
  • It serves as a technical baseline for "tamper-evident" data chains.

Operational policy

  • Issuers MUST NOT store original content. Hash-only inputs.
  • Issuers SHOULD apply rate limits to protect service availability.

Issuer disappearance and long-term verification

This specification explicitly defines proof validity as independent from the continued existence of the issuer.

  • The expiration, revocation, or disappearance of an issuer MUST NOT invalidate a proof retroactively.
  • Proof validity MUST rely solely on cryptographic verification against the public signing key that was active at the time of issuance.
  • Verifiers MUST NOT require a live endpoint operated by the issuer to validate an existing proof.
  • Verifiers MUST accept archived or historical public keys if they match the keyId referenced in the proof.
  • No destructive revocation mechanism MAY invalidate already-issued proofs.

Rationale: ProofSpec is designed as a long-term, self-contained proof format. Its validity is anchored in cryptography and archived public keys, not in the availability or authority of the original issuer.

Versioning

This document describes ProofSpec v0.1. Breaking changes to the canonicalization or validation logic MUST increment the major spec version.
