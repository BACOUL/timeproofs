Protocol (ProofSpec)

Defines how to create, sign, timestamp, and verify proofs that a specific data artifact existed at a point in time and has not changed since, without exposing the original content.

Spec: ProofSpec v0.1 · Effective: 2025-10-22 · Last updated: 2025-11-05 · See also: Regulatory Readiness

1. Overview

ProofSpec defines a minimal, open, and verifiable scheme to prove that a given artifact existed at time ts and remains unchanged. Privacy is preserved by hashing locally and transmitting only the digest. Verification is public and does not require contacting the original submitter.

  • Local hashing: original content never leaves the client.
  • Edge timestamp: server returns a signed tuple guaranteeing existence at ts.
  • Public verification: anyone can verify the tuple and signature.

2. Data model

{
  "hash": "hex(SHA-256(data))",
  "ts":   "Unix epoch ms",
  "sig":  "base64url(HMAC_SHA256(hash | ts, server_secret))",
  "type": "optional short string",
  "meta": { /* optional tiny JSON, non-personal */ }
}

Concatenation for signature is ASCII with delimiter | as hash|ts. The meta field must not contain personal data.

3. Create (client)

  1. Compute hash = SHA-256(data) locally.
  2. Prepare optional type and meta (small, non-identifying).
  3. POST to /api/timestamp with { hash, type?, meta? }.

Response: { hash, ts, sig, type?, meta? }.

4. Timestamp (server)

  • Validate hash as 64-hex.
  • Set ts = now() synchronized to trusted sources.
  • Compute sig = HMAC_SHA256("hash|ts") with a private key.
  • Store tuple in durable KV with id = hash.

5. Verify (public)

GET /api/verify?hash=... or POST /api/verify with {hash}.

  1. Lookup tuple by hash.
  2. Recompute HMAC("hash|ts") and compare with sig.
  3. Return status plus the tuple and echoes.
{
  "exists": true,
  "valid":  true,
  "hash":   "…",
  "ts":     1730670000000,
  "sig":    "…",
  "type":   "optional",
  "meta":   { /* optional */ }
}

6. Signatures & key lifecycle

  • Algorithm: HMAC-SHA256 over hash|ts.
  • Encoding: sig is Base64URL without padding.
  • Key rotation: maintain multiple active secrets; include kid if needed.
  • Lifecycle: generate with CSPRNG, store in HSM/secure vault, rotate on schedule, keep overlapping validity to support verify.

7. Text normalization (for hashing)

  • Encoding: UTF-8.
  • EOL: normalize to \n.
  • No BOM: strip UTF-8 BOM if present.
  • Binary: hash raw bytes as-is.
  • Clients MUST document whether input was text normalized or raw binary to reproduce the hash.

11. Security

  • TLS in transit; minimal logs; rate limits per IP/key.
  • Clock synchronization and monotonicity checks on ts.
  • Refuse malformed hashes; cap meta size; no personal data.
  • Key lifecycle per §6; publish kid map if public offline-verify is enabled.

12. Interoperability

  • Hashing: SHA-256 over bytes; apply §7 rules for text.
  • Transport: JSON over HTTPS; CORS for verification endpoints.
  • Offline verify: recompute HMAC if the verifying party holds the appropriate trust anchor for the key.

13. Spec versioning and deprecation

  • Version header: ProofSpec: v0.1 in responses.
  • Backward-compatible minors v0.1.x require no client change.
  • Breaking changes target v1.0 with migration window and deprecation schedule.
