Protocol (ProofSpec)

Defines how to create, sign, timestamp, and verify proofs that a specific data artifact existed at a point in time and has not changed since, without exposing the original content.

1. Overview

ProofSpec defines a minimal, open, and verifiable scheme to prove that a given artifact existed at time ts and remains unchanged. Privacy is preserved by hashing locally and transmitting only the digest.

  • Local hashing: original content never leaves the client.
  • Edge timestamp: server returns a signed tuple guaranteeing existence at ts.
  • Public verification: anyone can verify the tuple without contacting the original submitter.

2. RFC 2119 Terms

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY in this document are to be interpreted as described in RFC 2119.

3. Data model

{
  "hash": "hex(SHA-256(data))",
  "ts":   "Unix epoch ms",
  "sig":  "base64url(HMAC_SHA256(hash | ts, server_secret))",
  "type": "optional short string",
  "meta": { /* optional tiny JSON, non-personal */ },
  "kid":  "optional key id for rotation"
}

Signature input is ASCII with delimiter | as hash|ts. meta MUST NOT contain personal data and SHOULD be <= 512 bytes.

5. Create (client)

  1. Compute hash = SHA-256(data) locally. For text, normalize to UTF-8 with LF line endings; BOM MUST NOT be added.
  2. Prepare optional type and meta (small, non-identifying).
  3. POST to /api/timestamp with { hash, type?, meta? }.

Pseudocode:

// hashing (browser)
const buf = new TextEncoder().encode(text);
const digest = await crypto.subtle.digest('SHA-256', buf);
const hash = [...new Uint8Array(digest)].map(b=>b.toString(16).padStart(2,'0')).join('');
// create timestamp
await fetch('https://api.timeproofs.io/api/timestamp',{
  method:'POST', headers:{'Content-Type':'application/json','Accept':'application/json'},
  body: JSON.stringify({ hash, type:'event', meta:{ source:'spec' } })
});
# cURL
curl -sS -X POST https://api.timeproofs.io/api/timestamp \
 -H "Content-Type: application/json" \
 --data '{"hash":"<64-hex>","type":"event","meta":{"source":"spec"}}'

Large files: use streaming hashing (chunked) on client; do not upload content.

6. Timestamp (server)

  • Validate hash as 64-hex.
  • Set ts = now() from monotonic clock synchronized to multiple NTP sources. Max tolerated drift: ±1s.
  • Compute sig = HMAC_SHA256("hash|ts") with active secret kid.
  • Store tuple in durable KV under key hash.

7. Verify (public)

GET /api/verify?hash=... or POST /api/verify {hash}.

  1. Lookup tuple by hash.
  2. Recompute HMAC("hash|ts") using kid if present.
  3. Return status with exists, ts, sig, echoed fields.
{
  "exists": true,
  "hash":   "…",
  "ts":     1730670000000,
  "sig":    "…",
  "type":   "optional",
  "meta":   { /* optional */ },
  "kid":    "k1"
}
# cURL
curl -sS "https://api.timeproofs.io/api/verify?hash=<64-hex>"

8. Errors & Codes

  • 400 invalid hash format; meta too large.
  • 404 proof not found.
  • 413 request too large.
  • 429 rate limit exceeded.
  • 5xx transient server errors.

9. Security & Keys

  • TLS in transit; minimal logs; rate limits per IP/key.
  • Clock synchronization with multi-source NTP; monotonic checks on ts.
  • Key rotation: responses MAY include kid. Multiple active secrets MUST be supported during rotation.
  • Offline verify: a trust-anchor pack MAY be published to permit independent HMAC checks.
  • meta MUST exclude PII and SHOULD be ≤512 bytes.

10. Interoperability

  • Hashing: SHA-256 over bytes; text normalization rules documented above.
  • Transport: JSON over HTTPS; CORS open for verify endpoints.
  • OpenAPI: see /openapi.yaml for endpoints and examples.

11. Versioning & Deprecation

  • Response header: ProofSpec: v0.1.
  • Minor versions v0.1.x are backward compatible.
  • Breaking changes target v1.0 with a published migration window and dates.

Changelog (excerpt)

  • v0.1: base tuple {hash, ts, sig}, optional {type, meta, kid}.
