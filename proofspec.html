Protocol — ProofSpec

ProofSpec is the open, normative specification to prove when data existed and that it has not changed. TimeProofs v0.2 is a reference implementation providing a stateless API and portable .tproof.json receipts.

Overview

ProofSpec defines how to create, sign, publish, and verify digital proofs of existence.

Model: hash locally → get a signed, timestamped proof → anyone can verify later without access to your original data.

This document is normative for issuers and verifiers that claim to be ProofSpec v0.1 compliant.

Why ProofSpec matters

ProofSpec is designed as a foundation layer for trust across multiple domains:

  • AI provenance — record when a given AI output, prompt, or model snapshot existed and detect later tampering.
  • Data integrity — protect documents, datasets, binaries, and configuration files with verifiable, hash-based receipts.
  • Evidence & audit — provide a cryptographic anchor that can support legal workflows, audits, and compliance checks.
  • Interoperability — allow independent issuers and verifiers to cooperate around a simple, open proof format.

The goal is to make “hash locally, verify publicly or offline” a default pattern for any system that cares about integrity and time-bounded claims.

Normative language

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY in this document are to be interpreted as described in RFC 2119 and RFC 8174.

Normative scope & reference implementation

This document defines ProofSpec v0.1 as the normative specification. It also describes how TimeProofs v0.2 acts as a reference implementation.

Normative (ProofSpec v0.1)

  • Data model and required fields
  • Canonical signing string
  • Signature algorithms and verification rules
  • Validation requirements and error semantics
  • Versioning and compatibility requirements

Non-normative (TimeProofs v0.2 implementation choices)

  • Stateless API deployment model
  • Portable .tproof.json envelopes
  • Ed25519 public signatures and JWKS publication
  • Edge-native hosting details

Any implementation may claim ProofSpec v0.1 compliance without reproducing the TimeProofs v0.2 architecture, as long as the normative requirements of this document are met.

Conformance

The following roles are defined:

  • Issuer: a system that accepts a hash and returns a signed proof.
  • Verifier: a system that checks a proof and returns a validation result.
  • Client: any caller (app, backend, CLI, agent) that interacts with an issuer or verifier.

A ProofSpec-compliant Issuer:

  • MUST only accept canonical hashes and MUST NOT require original content.
  • MUST produce proof objects that satisfy the JSON schema and data model.
  • MUST sign the exact canonical signing string hash|ts (see Signing).
  • SHOULD include a stable verify URL for verification.

A ProofSpec-compliant Verifier:

  • MUST validate required fields and formats.
  • MUST recompute expected signature(s) according to alg and compare using a timing-safe method.
  • MUST return deterministic error codes (see Errors).

Canonicalization

  • Issuers and clients MUST hash the exact bytes they intend to prove (“bytes-in, bytes-out”).
  • Text inputs SHOULD be encoded as UTF-8 and SHOULD normalize line endings to LF (\n) before hashing.
  • Implementations MAY define additional deterministic canonicalization steps, but they MUST be documented if used.

.tproof.json format

A .tproof.json file is a portable envelope that carries a ProofSpec proof and minimal, non-sensitive context so it can travel with the artifact it protects.

Minimal recommended envelope

{
  "proof":{
    "hash":"<64-hex>",
    "ts":"2025-01-01T00:00:00.000Z",
    "sig":"<hex HMAC-SHA256>",
    "alg":"HMAC-SHA256",
    "kid":"v1",
    "issuer":"timeproofs.io",
    "verify_url":"https://api.timeproofs.io/api/verify?hash=..."
  },
  "artifact":{
    "name":"example.pdf",
    "media_type":"application/pdf",
    "bytes":183742,
    "created_at":"2025-01-01T00:00:00.000Z"
  },
  "meta":{
    "source":"ci-build"
  }
}
  • The proof object MUST be a valid ProofSpec v0.1 proof.
  • The envelope MUST NOT contain the original content.
  • The envelope SHOULD remain small and text-based.
  • Verifiers MAY accept either a raw proof object or a .tproof.json envelope containing it.

Signing

ProofSpec v0.1 defines a single canonical signing string. All compliant implementations MUST sign and verify the exact UTF-8 bytes of: 

<hash>|<ts>
  • hash MUST be lowercase hex (64 chars).
  • ts MUST be an ISO 8601 UTC timestamp ending with Z.
  • No whitespace, newline, or additional fields are allowed.

Signature algorithms

  • HMAC-SHA256 is REQUIRED for ProofSpec v0.1 compliance.
  • Ed25519 MAY be used as an additional public signature over the same canonical string.
// Node.js HMAC verify (example)
import crypto from "node:crypto";

function verify({ hash, ts, sig }, secret) {
  const msg = `${hash}|${ts}`;
  const expect = crypto.createHmac("sha256", secret).update(msg).digest("hex");
  return crypto.timingSafeEqual(Buffer.from(expect, "hex"), Buffer.from(sig, "hex"));
}

Validation

  • hash MUST be a 64-character lowercase hex string.
  • ts MUST be a valid ISO 8601 UTC timestamp and SHOULD NOT be unreasonably far in the future.
  • The verifier MUST recompute the expected signature(s) according to alg and compare using a timing-safe method.
  • If any required field is missing or invalid, the verifier MUST return a failure with an appropriate error code.

Security & guarantees

  • ProofSpec guarantees integrity and a time-bounded claim (“this hash existed at or before ts”).
  • ProofSpec does not prove authorship by itself; identity requires higher-layer systems.
  • Issuers MUST protect signing keys; compromise affects trust for newly issued proofs.
  • Clients SHOULD recompute the hash of the local artifact before verification.

For AI & Compliance

  • Privacy-first — only hashes and minimal metadata are processed.
  • Provider-neutral — independent issuers/verifiers can interoperate.
  • Compliance support — proofs can act as cryptographic anchors in audit workflows (e.g., AI Act / Data Act).
  • Offline verification — proofs and envelopes can be validated locally.

Verify URL

The verify URL is a stable endpoint that returns JSON status for the given hash or proof. It SHOULD be included in the proof JSON as verify_url.

Clients SHOULD keep the full proof JSON (or a .tproof.json envelope) for long-term and offline verification.

Proof bundle

  • Ship artifacts with a nearby proof (raw ProofSpec JSON or .tproof.json envelope).
  • Bundles SHOULD be small and MUST NOT contain personal data.

Reserved fields

Names starting with _tp_ are reserved and MUST NOT be used for custom metadata.

Operational policy

  • Issuers SHOULD keep minimal logs and avoid storing original content.
  • Issuers SHOULD apply rate limits and abuse protection on timestamp and verify endpoints.
  • Key rotation SHOULD be implemented using kid and a clear key lifecycle policy.

Checklist

  • Hash locally (no original content leaves the device).
  • Keep the proof JSON or a .tproof.json envelope.
  • Validate required fields and signature(s).
  • Prefer offline verification where possible for archival workflows.

Complementary protocols

ProofSpec defines the cryptographic proof layer. Independent, text-based companion protocols may document surrounding policies and transparency signals:

  • integrity.txt — tracking, cookies, logs/data use, third-parties, accessibility, change policy.
  • authenticity.txt — content origin (human/AI/mix), roles, disclosure, timeline.
  • rights.txt — allowed/forbidden use, licence, scope, update policy.
  • explainable-ia.txt — AI systems, uses, IO handling, explanations, limitations.

They follow the same pattern: a UTF-8 key:value file at the root and a self-integrity hash field (e.g., hash:<sha256>).

Governance & neutrality

  • ProofSpec defines a data model and signing rules, not an infrastructure stack.
  • Any organization can implement a compliant issuer/verifier, self-hosted or managed.
  • No blockchain or specific ledger is required.

Versioning & compatibility

ProofSpec v0.1 is the current normative core. Additive changes SHOULD be minor/patch; breaking changes MUST bump the major version.

TimeProofs v0.2 adds a stateless deployment model and .tproof.json envelopes while keeping the ProofSpec v0.1 proof object compatible.
