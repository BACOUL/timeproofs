# TimeProofs V1 Object Model

## Purpose

TimeProofs is the black box for AI actions. This document defines the TimeProofs V1 object model before implementation work begins.

The object model is needed to prevent confusion between the business traceability file, the canonical fingerprint, the TimeProofs Seal, and the lower-level proof object used for verification. It gives future API, SDK, specification, generator, and verifier work a shared vocabulary before any behavior changes are made.

This document is conceptual. It does not create a schema, change API behavior, change SDK behavior, implement canonicalization, add verification behavior, or create `.action.json` examples.

## Definitions

### Action File / AI Action File

An Action File, also called an AI Action File, is the business traceability file describing one observable AI action.

It is the product-level record. It explains what happened, which AI system or workflow produced or assisted the action, when it happened, and what customer-owned evidence or references the company wants to keep.

The Action File is customer-owned. The company stores it wherever it wants, such as its evidence repository, CRM, ticketing system, document store, legal archive, data lake, or internal audit system.

The Action File is not sent to TimeProofs by default.

Future `.action.json` work should represent this product-level Action File.

### Seal

A Seal is the cryptographic record proving that a canonical fingerprint was sealed at a specific time.

The Seal is created by TimeProofs for a fingerprint, not for sensitive action content. It may include issuer, issuedAt, nonce, keyId, algorithm, sealed fingerprint, signature, proof, or related verification fields.

A Seal must not be confused with proof that the AI action was correct. It does not prove that the content is true, that the business action was lawful, that legal validity is guaranteed, or that full compliance has been achieved.

### Proof Bundle / `.tproof.json`

A Proof Bundle is the lower-level technical proof object used to verify a sealed fingerprint.

Existing `.tproof.json` files are the current proof-bundle format. They remain backward-compatible and should continue to work with existing verification flows.

A Proof Bundle can be reused as a lower-level proof or seal primitive for future Action File work. It should not be confused with the Action File itself.

### Fingerprint

A fingerprint is the deterministic digest of the canonical hashable Action File content. It is computed locally before sealing.

TimeProofs seals fingerprints, not sensitive action content.

### Observable AI Action

An observable AI action is a concrete business action or system-visible event caused, assisted, or generated by an AI workflow.

Examples include creating a CRM lead, creating a support ticket, sending an email, generating a document, updating a CRM record, or classifying a request.

### Customer-Owned Evidence

Customer-owned evidence is any record, file, pointer, log reference, internal ID, document, ticket, CRM object, audit note, or trace kept by the company in its own environment.

The company controls the evidence and storage location. TimeProofs may seal a fingerprint of the evidence file, but it does not need to store the evidence by default.

### Sensitive Action Content

Sensitive action content is any data that should not be sent to TimeProofs by default. This can include prompts, model outputs, personal data, customer data, confidential business content, documents, emails, CRM records, internal notes, regulated data, credentials, or proprietary workflow details.

Sensitive action content may exist inside the company's own Action File if the company chooses to store it locally. It must not be uploaded to TimeProofs by default.

## Object Boundaries

### Action File Boundary

The Action File is the business traceability record.

It is customer-owned and stored by the company. It may contain:

- action summary
- system ID
- workflow ID
- action timestamp
- actor or automation identifiers
- model or tool references when appropriate
- business object references
- redaction notes
- internal IDs
- local evidence pointers
- links or references to technical logs
- customer-controlled context

It may contain sensitive content only if the company chooses to store that content locally in its own environment.

It must stay outside TimeProofs by default. TimeProofs should not require the full Action File to seal or verify a fingerprint.

### Seal Boundary

The Seal is the cryptographic record for a canonical fingerprint.

It is created by TimeProofs and should include sealing metadata such as:

- issuer
- issuedAt
- nonce
- keyId
- algorithm
- sealed fingerprint
- signature or proof fields
- verification metadata needed to check the seal

The Seal must not require sensitive action content. It should be designed around fingerprint-only sealing by default.

The Seal proves that the fingerprint was sealed at a time. It does not prove AI correctness, content truth, legal validity, or full compliance.

### Proof Bundle Boundary

The Proof Bundle is the portable lower-level proof object.

Existing `.tproof.json` Proof Bundles remain valid. A Proof Bundle can prove that a fingerprint was sealed and provide the information needed to verify that proof.

The Proof Bundle is not the Action File. It is proof metadata for a fingerprint, not the customer-owned business traceability record.

## Relationship Between The Objects

The conceptual relationship is:

Action File -> local canonical fingerprint -> Seal / Proof Bundle -> verification

The Action File is the record. The fingerprint is the digest of the canonical record. The Seal proves that TimeProofs sealed that fingerprint at a specific time. The Proof Bundle helps verify the seal or lower-level proof. The company keeps the Action File.

This separation is central to the TimeProofs privacy model:

- the company creates the Action File locally
- the company stores the Action File locally or in its own systems
- the company computes the canonical fingerprint locally
- TimeProofs receives only the fingerprint and minimal sealing metadata by default
- TimeProofs returns a Seal or Proof Bundle for verification
- sensitive action content stays under customer control by default

## Future `.action.json` Direction

`.action.json` is future work. This PR does not create a `.action.json` schema, example, generator, API, SDK helper, or verification behavior.

The intended role of `.action.json` is to represent the product-level Action File: the customer-owned business traceability file for one observable AI action.

`.tproof.json` remains the existing lower-level technical proof-bundle format.

`.action.json` and `.tproof.json` must not be merged into one confusing object:

- `.action.json` should represent the Action File record
- `.tproof.json` should remain the lower-level Proof Bundle format
- a Seal or Proof Bundle can reference the canonical fingerprint of an Action File
- verification can compare a local Action File fingerprint against the sealed fingerprint

Future design work should keep these objects separate unless a later specification defines a safe and clearly named envelope.

## Fingerprinting And Canonicalization Principles

These are high-level principles only. This document does not implement canonicalization.

Future canonicalization must be deterministic. The same hashable Action File core must always produce the same canonical fingerprint.

The fingerprint must not include fields that change after sealing. Mutable fields can create false mismatches and should remain outside the hashable core unless a later specification defines a stable rule.

The model must avoid circular hashing. The Seal, signature, proof fields, or sealed fingerprint must not be included inside the data that is hashed to produce that same fingerprint.

A detached Seal is preferred. Seal and proof data should remain outside the hashable Action File core unless a later specification defines otherwise.

The object model should support clear separation between:

- hashable Action File core
- non-hashable local annotations
- detached Seal
- detached or linked Proof Bundle
- verification result generated later by a verifier

## Sensitive-Content Boundary

TimeProofs must not receive sensitive action content by default.

Customers may store sensitive context in their own Action File if they choose. That storage decision belongs to the customer and should happen inside the customer's environment.

TimeProofs should receive only:

- the fingerprint
- minimal sealing metadata needed to issue and verify the Seal
- no prompts, outputs, customer records, emails, documents, or business content by default

Examples in future documentation, tests, or demos must use synthetic or redacted data.

The default privacy model is hash-only and fingerprint-only. Any feature that sends more than a fingerprint must be explicit, justified, documented, and outside the default path.

## Verification Model

Future Action File verification should explain exactly what is verified and what is not verified.

A verifier should be able to verify:

- fingerprint match
- seal or proof validity
- local Action File integrity if the fingerprint is computed locally

A verifier must also explain that it does not verify:

- AI correctness
- content truth
- legal validity
- full compliance

The future verification flow should work conceptually as follows:

1. Load the Action File locally.
2. Canonicalize the hashable Action File core locally.
3. Compute the canonical fingerprint locally.
4. Load or read the Seal or Proof Bundle.
5. Verify the Seal or Proof Bundle.
6. Compare the local fingerprint to the sealed fingerprint.
7. Display whether the local Action File still matches the sealed fingerprint.

The verification result is an interpretation of local integrity and proof validity. It is not legal advice, compliance certification, or proof that the AI action was correct.

## Backward Compatibility

Existing `.tproof.json` Proof Bundles remain valid.

Existing `/api/timestamp` and `/api/verify` behavior must not be broken by future Action File work.

Existing SDK helpers should remain compatible. New Action File support should be additive rather than replacing existing proof-bundle helpers.

Future `.action.json` support must not break existing `.tproof.json` verification.

A safe migration path should preserve the existing proof-of-existence primitives while adding Action File support on top of them.

## Non-Goals

This PR does not include:

- API changes
- SDK changes
- schema creation
- `.action.json` examples
- canonicalization code
- generator implementation
- verification behavior changes
- website implementation changes
- dashboard creation

- legal advice

- replacement of technical logs

TimeProofs complements technical logs. It does not replace them.

TimeProofs supports traceability evidence for fingerprints. It does not prove that the AI was correct, that the content is true, or that a legal or regulatory requirement has been fully satisfied.
