# TimeProofs — Handoff Protocol

Use this file when a new AI assistant, developer, advisor, or collaborator takes over the project.

## Mandatory reading order

1. `/TIMEPROOFS_MASTER_CONTEXT.md`
2. `/docs/startup/STARTUP_OPERATING_SYSTEM.md`
3. `/docs/startup/DECISION_LOG.md`
4. current branch history and latest commits
5. current protocol research documents
6. current product/pack specs

## First actions for a new AI assistant

Before proposing changes:

- confirm the active branch
- inspect recent commits
- identify which decisions are settled vs open
- verify current MCP/A2A/UCP/AP2 facts online if the answer depends on protocol state
- check whether new competitor or standard changes invalidate assumptions
- do not revive AgentReady positioning by default
- do not propose a generic dashboard/API/landing-page bundle unless the actual workflow requires it

## Project summary in one paragraph

TimeProofs is being relaunched from an older AgentReady scanner/CI product into cross-protocol consistency infrastructure for agentic transactions. The initial wedge is deterministic UCP ↔ AP2 consistency verification; the long-term platform is a Cross-Protocol Consistency & Invariant Engine. The strategic thesis is that protocol objects can each be locally valid while their composition is globally inconsistent. The expected moat is not basic comparison logic but versioned, verified Invariant Packs containing mappings, canonicalization, compatibility knowledge, evidence rules and regression fixtures. The company is intended to be built as a global developer-infrastructure startup, with world-class product, developer experience, distribution, reliability, security, economics and design.

## Things not to assume

Do not assume:

- the 12 candidate UCP/AP2 invariants are final
- pricing is final
- open source strategy is final
- a web dashboard is required
- an API must exist before CLI/local use proves useful
- every previous AgentReady component should be reused
- every protocol claim from an old conversation is still current

## Required standard for new proposals

Any major proposal should state:

- problem
- evidence
- affected protocol boundary
- why one protocol cannot solve it alone
- current competitors
- absorption risk
- user and payer
- distribution path
- moat contribution
- implementation cost
- reliability/security implications
- whether it strengthens or distracts from the platform trajectory

## Handoff completion rule

Before ending substantial work, update the canonical docs if any of these changed:

- company thesis
- wedge
- protocol assumptions
- invariant semantics
- architecture
- pricing/packaging
- distribution thesis
- open source boundary
- major risks
- roadmap priority

Conversation memory is never the canonical project state. The repository is.
