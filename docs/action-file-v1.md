# TimeProofs Action File v1 Specification

Status: V1 design specification  
Scope: documentation and schema foundation only  
Related docs: `docs/objects-model.md`, `docs/hash-model.md`, `docs/proof-levels.md`  
Related registry: `schemas/action-types.json`  
Related draft schema: `schemas/action-file-v1.schema.json`

## 1. Purpose

The TimeProofs Action File v1 format defines the customer-owned business record for one observable AI action.

It is designed for the TimeProofs positioning: the black box for AI actions.

An Action File should make it possible to reconstruct what was recorded about an AI-assisted action, what level of evidence was attached to it, what fingerprint was sealed, and what the file does not prove.

This specification is a foundation document. It does not implement generation, sealing, verification, API routes, SDK helpers, dashboard behavior, billing, or legal certification.

## 2. Core Principles

Action File v1 follows these principles:

1. one file describes one observable AI action;
2. the customer owns the Action File;
3. TimeProofs seals a fingerprint, not sensitive action content;
4. the hashable core must be deterministic;
5. seal, proof, signature, verification result, and local annotations must remain outside the hashable core;
6. existing `.tproof.json` proof bundles remain compatible;
7. verification proves integrity of the sealed relationship, not truth, correctness, legality, or compliance.

## 3. File Extension

The recommended future file extension is:

```text
.action.json
```

Example:

```text
crm-lead-created-2026-06-16.action.json
```

This extension is a product convention. It does not change existing `.tproof.json` support.

## 4. Top-Level Structure

A future Action File v1 should use this top-level structure:

```json
{
  "format": "timeproofs.action.v1",
  "schema_version": "1.0.0-design",
  "action_core": {},
  "integrity": {},
  "local_annotations": {},
  "verification_result": {}
}
```

Only `format`, `schema_version`, and `action_core` belong to the canonical hashable payload.

`integrity`, `local_annotations`, and `verification_result` must not be included when computing `integrity.payload_hash`.

## 5. Hashable Payload Boundary

The canonical hashable payload is:

```json
{
  "format": "timeproofs.action.v1",
  "schema_version": "1.0.0-design",
  "action_core": {}
}
```

The payload hash is:

```text
sha256(canonical_json({ format, schema_version, action_core }))
```

The implementation must follow `docs/hash-model.md`.

The following fields must never be included in the hashable payload:

- `integrity`
- `integrity.payload_hash`
- `integrity.seal`
- `integrity.proof_bundle`
- `integrity.signature`
- `local_annotations`
- `verification_result`
- generated verifier warnings
- generated verifier timestamps
- viewer-specific metadata
- export metadata added after sealing

## 6. Required Top-Level Fields

### 6.1 `format`

Required value:

```text
timeproofs.action.v1
```

This identifies the file family.

### 6.2 `schema_version`

Recommended initial value:

```text
1.0.0-design
```

Future production schemas may use a strict semantic version.

### 6.3 `action_core`

Required.

The stable business-readable core of the Action File.

### 6.4 `integrity`

Recommended when the Action File has been hashed, sealed, or prepared for sealing.

It contains the payload hash and future Seal or Proof Bundle references.

### 6.5 `local_annotations`

Optional.

Customer-owned mutable local notes or display data. This is explicitly non-hashable.

### 6.6 `verification_result`

Optional.

Generated by a verifier after checking the file. This is explicitly non-hashable.

## 7. `action_core` Structure

The `action_core` object is the stable record of the AI action.

Recommended structure:

```json
{
  "action_id": "act_01HYPOTHETICAL",
  "created_at": "2026-06-16T17:00:00Z",
  "actor": {},
  "action": {},
  "proof_level": "target_confirmed",
  "workflow": {},
  "target_system": {},
  "evidence": {},
  "redaction": {},
  "limitations": [],
  "metadata": {}
}
```

### 7.1 `action_id`

Required.

A stable customer-side identifier for the recorded action.

It should not contain sensitive personal data.

### 7.2 `created_at`

Required.

The Action File creation timestamp or stable record timestamp.

Use ISO 8601 UTC when possible.

### 7.3 `actor`

Required.

The AI agent, automation, workflow, human, system, or hybrid actor that produced or recorded the action.

Recommended structure:

```json
{
  "type": "ai_agent",
  "id": "agent_support_triage_v1",
  "name": "Support triage agent",
  "version": "1.0.0"
}
```

Allowed actor types:

- `ai_agent`
- `automation`
- `human`
- `system`
- `hybrid`

### 7.4 `action`

Required.

The observed or recorded action.

Recommended structure:

```json
{
  "type": "support.ticket_created",
  "status": "target_confirmed",
  "summary": "Created a support ticket from an incoming customer request.",
  "occurred_at": "2026-06-16T17:00:00Z"
}
```

The `type` should align with `schemas/action-types.json` when possible.

Allowed V1 status values:

- `declared`
- `executed`
- `target_confirmed`
- `failed`
- `partial`
- `cancelled`

### 7.5 `proof_level`

Required.

Allowed values:

- `declared`
- `executed`
- `target_confirmed`
- `externally_verifiable`

Definitions are in `docs/proof-levels.md`.

### 7.6 `workflow`

Optional but recommended when the action was produced by an automation, agent, or integration.

Recommended fields:

- `provider`
- `workflow_id`
- `run_id`
- `step_id`
- `environment`

### 7.7 `target_system`

Required for `target_confirmed` and recommended for `externally_verifiable`.

Recommended fields:

- `name`
- `type`
- `object_type`
- `reference`
- `confirmed_at`

Example references:

- CRM lead ID
- ticket ID
- message ID
- file ID
- record ID
- delivery ID

### 7.8 `evidence`

Recommended.

The `evidence` object contains references or fingerprints of customer-owned evidence.

It should not require raw sensitive content.

Recommended structure:

```json
{
  "references": [
    {
      "type": "target_response_fingerprint",
      "label": "CRM API response fingerprint",
      "reference": "crm-response-2026-06-16-001",
      "fingerprint": "sha256:<hex>",
      "stored_by": "customer"
    }
  ]
}
```

### 7.9 `redaction`

Recommended when sensitive content is omitted, hashed, or replaced by references.

Recommended fields:

- `applied`
- `profile`
- `notes`

### 7.10 `limitations`

Recommended.

A list of short, stable statements explaining the limits of the Action File.

Examples:

- `TimeProofs does not verify the target system content.`
- `This file does not prove that the AI output was correct.`
- `Sensitive content is stored by the customer and represented by fingerprints.`

### 7.11 `metadata`

Optional.

Stable non-sensitive metadata controlled by the customer.

Metadata should not contain secrets, credentials, personal data, raw prompts, raw outputs, or sensitive business content unless the customer explicitly chooses to include them in its own locally stored Action File.

## 8. `integrity` Structure

The `integrity` object is outside the hashable core.

Recommended structure:

```json
{
  "canonicalization_profile": "timeproofs-json-canonical-v1",
  "hash_algorithm": "sha256",
  "payload_hash": "sha256:<hex>",
  "seal": {}
}
```

### 8.1 `canonicalization_profile`

Identifies the deterministic JSON canonicalization profile.

Future implementations should align with RFC 8785 / JCS where possible or document deviations.

### 8.2 `hash_algorithm`

Recommended value:

```text
sha256
```

### 8.3 `payload_hash`

The hash of the canonical hashable payload.

It must not be included in the hashable payload itself.

### 8.4 `seal`

Optional until a future sealing endpoint exists.

A future Seal may include:

- issuer
- issued timestamp
- key ID
- signature algorithm
- signature
- proof bundle reference

The Seal must remain outside the hashable payload.

## 9. `local_annotations`

`local_annotations` is optional and mutable.

Examples:

- local review notes
- folder name
- user-facing label
- internal case owner
- UI tags
- export notes

Changing `local_annotations` must not invalidate the payload hash because it is outside the hashable payload.

## 10. `verification_result`

`verification_result` is optional and generated after verification.

It may include:

- verification status
- verifier version
- checked timestamp
- warnings
- mismatch reason
- key status
- supported schema status

It must not be included in the hashable payload.

## 11. Proof Level Rules

The Action File must include one of the proof levels from `docs/proof-levels.md`.

### 11.1 `declared`

The file declares a recorded AI-related action, but execution and target confirmation are not established.

### 11.2 `executed`

The workflow, automation, AI agent, or application reports that the action was executed, but no target-system confirmation reference is present.

### 11.3 `target_confirmed`

The Action File includes a target-system confirmation reference such as a lead ID, ticket ID, message ID, file ID, record ID, case ID, or delivery ID.

### 11.4 `externally_verifiable`

The Action File includes a reference or method that a reviewer may be able to compare against an external or independent system, subject to access rights.

## 12. Privacy Rules

Action File v1 must preserve the TimeProofs privacy-first model.

Default V1 behavior should be:

- compute the payload hash locally;
- send only the payload hash and minimal sealing metadata to TimeProofs;
- keep sensitive content in the customer environment;
- use fingerprints or references for prompts, outputs, documents, API responses, and message bodies;
- use synthetic or redacted examples in public docs;
- never require raw prompts, raw outputs, customer records, emails, personal data, secrets, credentials, or internal logs to be sent to TimeProofs by default.

## 13. Verification Semantics

A valid verification can mean:

- the hashable payload still matches the sealed payload hash;
- the Seal or Proof Bundle is valid under the supported verification model;
- the file has not changed in the hashable sections since sealing;
- the proof level states what evidence is represented.

A valid verification does not mean:

- the AI output was correct;
- the action was lawful;
- the action was fair;
- the business decision was valid;
- the file contains every relevant fact;
- a regulator, court, insurer, auditor, partner, or customer will accept it;
- TimeProofs has reviewed the underlying content.

## 15. Backward Compatibility

This specification does not change existing v0.2 behavior.

Existing `.tproof.json` Proof Bundles remain valid.

Existing routes remain unchanged:

- `POST /api/timestamp`
- `POST /api/verify`

Future Action File support must be additive.

## 16. Non-Goals

This specification does not:

- implement `.action.json` generation;
- implement canonicalization code;
- implement hashing helpers;
- implement `/api/seal`;
- implement `/api/verify-seal`;
- modify existing `/api/timestamp`;
- modify existing `/api/verify`;
- modify `verify.html`;
- modify SDK helpers;
- modify self-host behavior;
- modify OpenAPI;
- create a dashboard;
- create billing;
- provide legal certification;
- claim regulatory compliance.

## 17. Next Step

After this specification is accepted, the next safe PR should add synthetic `.action.json` examples and test vectors, or define the canonicalization profile in a separate document before implementing helpers.
