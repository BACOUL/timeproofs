# TimeProofs Sales — Pilot Offer Pack

Phase: G — market validation  
Purpose: convert serious replies into paid pilots before building the full SaaS

## Pilot principle

A pilot must be narrow enough to sell quickly and useful enough to validate willingness to pay.

Do not sell a platform. Sell one workflow.

Do not promise full compliance, legal proof, AI correctness, dashboard access, API keys, self-hosting or broad integrations.

Sell this:

> We map one important AI action, create one Action File pattern, seal its fingerprint, and show how the organization can verify what happened later.

## What TimeProofs proves in a pilot

A pilot can show:

- a specific AI action can be represented in a clear Action File
- the Action File can be hashed consistently
- the fingerprint can be sealed by TimeProofs
- the file can be verified later
- the workflow can be explained to non-technical stakeholders
- the company can keep the Action File and original evidence in its own environment

A pilot does not prove:

- the AI was correct
- the business action was legally valid
- the organization is fully compliant
- technical logs are unnecessary
- TimeProofs should store sensitive content

## Pilot qualification checklist

Before proposing a paid pilot, confirm:

- the AI workflow exists or is actively being built
- the AI creates, updates, sends, classifies, routes or generates something
- there is a real reason to reconstruct the action later
- the prospect understands hash-only sealing
- the prospect accepts the limitation language
- there is a clear workflow owner
- there is at least one person who could approve payment
- the pilot can be scoped to one workflow

## Discovery call structure

Target length: 20 minutes

### 1. Context — 3 minutes

Ask:

- What AI workflows are you using or building?
- What does the AI actually do beyond text generation?
- Which system does it act inside?

### 2. Workflow — 5 minutes

Ask:

- What action is created or changed?
- Is there a target record ID?
- Who receives or uses the result?
- What proof currently exists?

### 3. Risk — 5 minutes

Ask:

- What happens if the AI action is wrong or disputed?
- Who investigates?
- Are current logs understandable by non-technical stakeholders?
- Has a customer, manager, auditor or partner ever asked what happened?

### 4. Pilot fit — 5 minutes

Ask:

- Would one Action File for this workflow be useful?
- What proof level would matter: declared, executed, target_confirmed, externally_verifiable?
- What would block a paid pilot?
- Would 299 EUR or 499 EUR be acceptable for a narrow validation?

### 5. Close — 2 minutes

Say:

The next step would not be a full integration. It would be one workflow, one Action File pattern, one Seal and one verification walkthrough. I can scope it as a 299 EUR simple pilot or a 499 EUR deeper workflow pilot.

## Proof levels for pilot discussion

| Proof level | Meaning | Example |
|---|---|---|
| declared | The system declares that an action was intended or prepared | AI prepared an email draft |
| executed | The workflow records that the action was executed | automation sent the API request |
| target_confirmed | The target system confirms the result | CRM returns lead ID |
| externally_verifiable | There is an independent external reference | public record, external signature or third-party confirmation |

Default pilot recommendation: start with `target_confirmed` when possible.

## Pilot acceptance criteria

At the end of the pilot, the result should answer:

1. Is the Action File understandable?
2. Is the Seal/Verify flow credible?
3. Does the workflow owner see value?
4. Is the limitation language acceptable?
5. Is there willingness to continue or pay for more?

## Pilot refusal reasons to record

If the prospect refuses, record the reason:

- price too high
- problem not urgent
- no current AI action workflow
- logs considered sufficient
- buyer unclear
- privacy concern
- legal/compliance uncertainty
- integration too hard
- wants dashboard first
- wants self-host first
- wants formal certification
- timing not right

## Go signal from pilot

A pilot counts as strong validation when at least one is true:

- pilot is paid
- prospect asks for invoice or payment details
- prospect commits to testing on a real workflow
- agency wants to test with a real client
- company identifies internal buyer and workflow owner
- developer starts implementing `/api/seal`
- risk/ops/legal stakeholder asks for internal review

## No-Go signal from pilot

A pilot does not validate the market when:

- prospect only wants free advice
- no workflow exists
- no owner exists
- no budget exists
- the use case is purely theoretical
- the product is understood but not valuable
- the prospect only wants a full SaaS without paying for a pilot
