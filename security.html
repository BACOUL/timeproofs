Security verification

  • Headers policy: enforced via CSP + hardened defaults (no framing, no mixed content, restrictive permissions).
  • Static site posture: no server-rendered sessions, no user accounts, no content upload.
  • API posture: hash-only inputs; public verification endpoint; strict input validation.

When production is live, you can validate externally using tools like SecurityHeaders, SSL Labs, and PageSpeed — but this page avoids hard-coded scores.

  • Service Worker allowed: worker-src 'self' blob:.

Rate limits

  • GET /api/verify: limited per IP (anti-scrape / anti-flood).
  • POST /api/timestamp: limited per IP/token; strict hash validation; predictable errors.

Exact thresholds are implementation controls and may change; clients should handle 429 with retry/backoff.

Key policy

  • Signing: HMAC-SHA256 (reference implementation).
  • Rotation: keys are rotated and separated per environment (dev/staging/prod).
  • Design direction: support for additional verifiers without changing ProofSpec (e.g., public keys via JWKS if introduced).
// Node.js verify example (HMAC)
import crypto from "node:crypto";
function verify({hash, ts, sig}, secret){
  const msg = `${hash}|${ts}`;
  const expect = crypto.createHmac("sha256", secret).update(msg).digest("hex");
  return crypto.timingSafeEqual(Buffer.from(expect,'hex'), Buffer.from(sig,'hex'));
}

Logging & retention

  • No original content stored. Hash-only inputs and minimal proof fields.
  • Operational logs are minimized and purpose-bound (abuse prevention, reliability).
  • Privacy details are documented on Privacy.

Vulnerability disclosure

Report security issues via /.well-known/security.txt. Include reproduction steps, impact, and affected endpoints. Responsible disclosure is expected.

Dependencies

  • Dependency updates are tracked and reviewed before release.
  • Build output is static; runtime is reduced to the minimum required.

Source: GitHub (v0.2 branch)

Status & errors

  • /api/ping → HTTP 200 when healthy.
  • Error format: {"ok":false,"error":"..."} with 4xx/5xx.
  • Clients should treat verification as read-only and safe to retry.
