Security / Seal model

Security for verifiable AI Action Files.

TimeProofs protects the integrity of Action Files through local hashing, canonical payload hashes, asymmetric signatures, public keys, and verifier behavior that avoids sensitive-content upload by default.

Local hashingCanonical payload hashAsymmetric signaturesNo blockchain by default
Security boundary: TimeProofs verifies the relationship between an Action File payload hash and a TimeProofs Seal. It does not prove that the AI output was correct, lawful, complete, or accepted by a third party.

Action File security flow

1. AI actionBusiness system records an observable action.
2. Action FileThe company creates a structured .action.json.
3. Local hashCanonical payload is hashed locally.
4. SealTimeProofs signs the payload hash.
5. VerifyVerifier recomputes and checks signature.

Local hashing and canonical payload hash

Local hashing

Content stays with the company

The Action File payload hash can be calculated in the browser, CLI, SDK, or company environment before any Seal request.

Anti-circular rule

Seal fields are excluded

The canonical payload hash excludes the Seal, signature, verifier result, and other mutable proof fields to avoid circular hashing.

TimeProofs Seal and asymmetric signatures

  • TimeProofs signs a Seal payload, not raw sensitive AI content.
  • The Seal payload contains the canonical payload hash, format, action id, sealed timestamp, signature algorithm, and public_key_id.
  • The preferred model is asymmetric signing, with Ed25519 as the target algorithm where supported.
  • The private signing key must stay server-side or in controlled key-management infrastructure.
  • The public key is published so verifiers can check signatures independently.

Public key id and key rotation

Active keys

Used for current Seals and published with a stable public_key_id.

Retired keys

Kept available for historical verification of existing Seals.

Compromised keys

Remain listed with clear incident state and guidance, instead of being silently removed.

Public key registry: /.well-known/timeproofs-keys.json. Human guidance: keys.html.

Verifier behavior

  • Rebuild the hashable Action File payload locally.
  • Recompute the canonical payload hash.
  • Compare the recomputed hash with the Seal payload hash.
  • Use the referenced public_key_id to verify the signature.
  • Return clear statuses such as valid, modified payload, invalid signature, unknown key, retired key, or unsupported format.

Threat model: protected and not protected

Protects
  • Accidental or malicious Action File modification after sealing.
  • Mismatch between a Seal and a changed payload.
  • Forgery attempts when the public key does not validate the signature.
  • Silent key replacement when key ids and statuses are preserved.
Does not protect
  • Incorrect AI reasoning or hallucinations.
  • Illegal, unauthorized, or invalid business actions.
  • Bad evidence placed inside the Action File by the company.
  • Compromised company storage, devices, CRM, or internal access controls.

No blockchain by default and no overclaims

TimeProofs V1 focuses on signed/verifiable Action Files and public key verification. Blockchain anchoring is not required by default and should not be presented as active unless implemented later.

  • No absolute legal proof guarantee.
  • No full AI Act or GDPR compliance guarantee.
  • No court-ready assurance.
  • No guarantee that a customer, auditor, insurer, regulator, bank, or court will accept the record.
