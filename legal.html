Overview

This Legal page sets baseline terms for using the TimeProofs website, protocol drafts (ProofSpec), reference APIs (v0.1/v0.2), official SDK/CLI, and offline/local verification tools (collectively, the “Service”).

By using the Service, you agree to these Terms and the Privacy Policy. If you use the Service for an organization, you represent you have authority to bind that organization. Minimum age: 16.

Third-party implementations that do not use the official Service are outside the scope of these Terms and are governed by their own operators.

Normative language

Where this page uses MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY, these words describe requirements for using the Service safely and lawfully, especially regarding acceptable use and data handling.

“Example” content is informative and does not create additional requirements beyond what is stated as MUST/MUST NOT.

Conformance

  • You MUST comply with applicable law and these Terms when using the Service.
  • You MUST submit hashes only (and permitted minimal metadata where supported) and MUST NOT upload original content to TimeProofs endpoints unless explicitly required by a future feature.
  • You MUST NOT include personal data or sensitive information in meta.
  • If API keys are issued, they are confidential; you are responsible for activity under your key.

Canonicalization

TimeProofs is designed around “hash-only” operation. You are responsible for hashing the correct bytes for your use-case and for preserving your own original data and context. If you hash text, you SHOULD normalize it consistently (for example, UTF-8 and LF), so later verification matches what you intended to prove.

Data model

  • Service: websites, official APIs, SDK/CLI, offline/local tools, and any hosted UI operated under timeproofs.io and subdomains.
  • Hash: irreversible digest of input content. In v0.2, this is intended to be SHA-256.
  • Proof: signed record (for example: hash, ts, sig, and optional metadata) attesting a hash existed at a time.
  • Bundle (.tproof.json): structured JSON document containing a proof plus protocol metadata.
  • Meta: optional small JSON you provide. It MUST NOT contain personal data or sensitive information.
  • Offline tools: SDK/CLI/verify UIs capable of creating or verifying proofs without sending original content to TimeProofs.

Proof format

Proofs and bundles are defined by the ProofSpec and related documentation. This Legal page does not redefine the format; it defines how you may use it and the limits of what it proves.

A cryptographic proof is evidence that a specific hash was recorded and signed at time ts. It does not, by itself, prove authorship, delivery, reading, identity, intent, or legal qualification.

Signing

  • Online proofs are signed by TimeProofs infrastructure using documented algorithms (for example HMAC-SHA256, and optionally asymmetric keys such as Ed25519 as documented).
  • Signatures provide technical integrity and timestamp assurances only. They are not, by themselves, qualified electronic signatures or trust services under eIDAS or similar frameworks.
  • You are responsible for secure storage of your bundles/proofs and for secure handling of any local secrets used by offline tooling.

Validation

  • You SHOULD verify proofs/bundles using official tools or compatible verifiers and keep the full proof JSON for long-term verification.
  • If verification fails (invalid hash/signature/structure), you MUST treat the proof as untrusted.
  • You MUST NOT misrepresent failed verification as a valid proof.

JSON schema

Proof/bundle schemas are described in the protocol documentation. If you integrate the Service, you SHOULD validate bundles against the published schema and handle errors safely.

Test vectors

Protocol test vectors (where provided) are for technical verification. They do not create legal commitments or warranties.

Verification

  • Hosted verification endpoints may enforce rate limits and abuse protection.
  • Verification results are provided for technical validation only and are not legal advice.

Verify URL

  • Verify URLs are intended to be stable, but in beta they may change for operational or security reasons.
  • You SHOULD keep the full proof JSON (.tproof.json) and SHOULD NOT rely exclusively on a URL for long-term archival use.

Proof bundle

  • Bundles SHOULD be small, self-contained, and MUST NOT include personal data or sensitive information in meta.
  • Offline inspection SHOULD be possible without contacting the issuer. Online verification MAY be used to re-check status or keys.
  • You are responsible for storing your bundles, proofs, and any underlying source content.

Reserved fields

Protocol-reserved fields (for example names starting with _tp_ where documented) MUST NOT be repurposed in a way that creates ambiguity or misleads verifiers.

Errors

  • We may return errors such as invalid hash, invalid signature, not found, or rate limited.
  • You MUST implement safe error handling and MUST NOT attempt to bypass rate limits or abuse protections.

Operational policy

  • Fair use: adaptive rate limits per IP/key may be enforced on API v0.1 and v0.2 to protect stability.
  • Abuse: excessive traffic, scraping, or attempts to bypass protections may be throttled or blocked.
  • Security: report vulnerabilities to security@timeproofs.io or see security.txt. Do not disclose before coordinated remediation.
  • Changes: the Service is public beta; features may change, be rate-limited, or be discontinued. No SLA in v0.2.

Checklist

  • Hash locally and keep your source content and context.
  • Store the full proof/bundle (.tproof.json), not just a URL.
  • Do not include personal data or sensitive info in meta.
  • Respect rate limits and acceptable use rules.

Versioning

  • These Terms apply to the beta stage (v0.2). We may update them; changes will be reflected by the updated date/version.
  • Protocol versions (ProofSpec) and API versions are documented separately; you SHOULD check compatibility before relying on a specific behavior.
